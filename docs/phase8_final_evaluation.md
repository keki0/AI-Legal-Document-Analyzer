# Phase 8 — Final Evaluation & Integration

## 1. Objective

Demonstrate that the components built in Phases 1–7 work together on real
documents, and that a generated sentence can be traced back to the page of the
PDF it came from.

This is a **validation phase, not a model-development phase**. No model was
trained, no methodology was changed, and no earlier result was recomputed.

## 2. Integrated architecture

`src/pipeline.py` contains **no analysis logic of its own**. Every stage is a
call into the module that owns it; the integration layer adds only sequencing,
the join on `clause_id`, and failure isolation.

```
PDF
 -> extract_document / segment_clauses         Phase 1
 -> ClauseClassifier.predict                   Phase 3
 -> analyze_clauses  (calibration, salience, flags)   Phase 4
 -> attach_extractions                         Phase 5
 -> build_improved -> RAGContextBuilder        Phase 1 / 6
 -> GenerationPipeline.run                     Phase 7
```

A test (`test_pipeline_reimplements_no_phase_logic`) fails if `pipeline.py`
ever contains `re.compile`, `SentenceTransformer`, `AutoModel`, `softmax`,
`TfidfVectorizer` or `_FLAG_DEFINITIONS` — the signatures of logic copied out
of the module that owns it. Duplicated logic drifts; this is a guard against
that.

Two structures are added: `DocumentAnalysis` (one document, all stages) and
`QueryResult` (one question against one document).

## 3. Documents evaluated

The two existing fixtures, unchanged:

- `sample-independent-contractor-agreement.pdf` — 3 pages, numbered clauses,
  an **unfilled template** whose dates and amounts are all placeholders
  (Phase 5 finding).
- `synthetic-unnumbered-policy.pdf` — generated by the existing
  `scripts/make_policy_fixture.py`; prose headings with no numbering, which the
  Phase 1 baseline regex cannot segment at all.

No new dataset or document was introduced.

## 4. Integration workflow

`analyze_document(path)` runs Phases 1–6 and returns a `DocumentAnalysis`.
Generation is deliberately **not** part of it: generation is per-query, and
analysing a document should not require loading FLAN-T5.

`ask(analysis, query, task)` builds a Phase 6 context and generates from it.
Query failures are captured in the result rather than raised, so one bad query
cannot abort a batch.

**Degraded mode.** The classifier is a downloaded artefact and may be absent.
Rather than crashing, the pipeline marks clauses `Unclassified`, sets
`degraded=True`, and continues — flags and extraction are rule-based and still
work. Degradation is always recorded, never silent, so an interface can tell
the user categories are missing instead of showing blanks.

## 5. Provenance flow

The clause identifier is the join key throughout:

```
Clause.clause_id
  -> ClauseAnalysis.clause_id
  -> ExtractedItem.clause_id
  -> RetrievalResult.clause_id
  -> RetrievedClause.clause_id
  -> GeneratedResponse.source_clause_ids
```

`test_clause_id_survives_from_pdf_to_generated_response` asserts the identifier
is unchanged at every hop and that each retrieved id resolves to exactly one
analysis. Every response also carries citations of the form
`Clause 6: Intellectual Property (p2)`.

## 6. Representative queries

Eleven queries across the two documents, one per topic the documents actually
contain: intellectual property, termination and notice, confidentiality,
payment, governing law and dispute resolution, liability and indemnity, a
multi-clause summary, data sharing, automatic renewal, policy dispute
resolution, and data retention.

The set is deliberately small. Padding it would inflate the counts without
testing anything new, and no accuracy metric depends on its size.

## 8. Representative Query Results

The end-to-end queries demonstrate successful operation of the **retrieval → RAG → generation** chain, but also expose realistic failure modes.

### Successful Examples

#### Intellectual Property

**Query:**

> Who owns the work produced by the contractor?

**Retrieved clauses:**

1. Intellectual Property
2. Independent Contractor Status
3. Indemnification

**Generated answer:**

> The Contractor agrees to assign all rights, title, and interest to the Client upon full payment.

The response was sourced to **Clause 6, Intellectual Property**, and the retrieved clause contains exactly this work-product ownership obligation.

#### Confidentiality

**Query:**

> What information must the contractor keep confidential?

The **Confidentiality** clause was ranked first, and the generated response stated that the Contractor must not disclose or use confidential or proprietary information belonging to the Client.

#### Automatic Renewal

**Query:**

> Does my subscription renew automatically?

The **Automatic Renewal of Your Subscription** clause was ranked first, with the **automatic-renewal flag** attached.

#### Data Retention

The policy query asking how long data is retained retrieved **How Long We Keep Your Data** as the top clause.

The extraction layer also identified the **twenty-four-month duration** from the clause.

## 9. Failure Analysis

The integrated run demonstrates that **successful retrieval and structural grounding do not guarantee a correct generated answer**.

### Generation/Selection Failure Despite Correct Retrieval

For:

> How and when is the contractor paid?

**Payment Terms** was correctly ranked first. However, FLAN-T5 generated:

> The Contractor is solely responsible for any local, federal, or international tax obligations.

The retrieved **Payment Terms** clause contains the actual rate, milestone, invoicing, and payment information, but the model selected the peripheral tax sentence instead.

This is therefore classified as a **generation/selection failure**, not a retrieval failure.

A similar case occurred for:

> Summarize the payment and termination terms.

Both relevant clauses were retrieved, but the generated response focused heavily on the tax sentence before providing limited payment information.

### Incorrect Generation for Governing-Law Query

For:

> Which law governs the agreement and how are disputes resolved?

**Miscellaneous** was correctly retrieved first and contains both the governing-law and dispute-resolution provisions.

However, the generated response was unrelated:

> If you are a contractor, you must sign a contract with the contractor. If you do not sign the contract, the contractor will not be able to terminate the contract.

The response was structurally associated with **Clause 10**, but its content does not correctly answer the question.

This demonstrates that **structural provenance is not equivalent to semantic correctness**.

### Retrieval Failure

For:

> Who else can see my personal data?

The system ranked **Your Rights and Choices** first and **Sharing With Third Parties** second.

The generated answer therefore described access, correction, and deletion rights rather than third-party data sharing.

This represents a **retrieval-ranking failure** because the more relevant clause existed but was not ranked first.

### Interpretation

These cases reinforce the layered evaluation strategy used throughout the project:

```text
Classification quality
        ↓
Retrieval quality
        ↓
Context quality
        ↓
Generation quality
        ↓
End-to-end answer quality
```

A successful earlier stage does not guarantee success at a later stage.

## 11. Limitations

- The end-to-end evaluation covers only **two documents**.
- One document is a **synthetic policy fixture**.
- The contractor agreement is an **unfilled template containing placeholders**.
- The 11-query evaluation is intended to validate integration, not provide statistically significant performance estimates.
- No end-to-end accuracy metric is reported because there is no ground truth for the complete pipeline.
- Structural `is_grounded=True` means that a source clause was attached to the response; it does **not** guarantee that every generated statement is correct.
- Phase 7 demonstrated that **FLAN-T5 can introduce unsupported information** even when the correct clause is retrieved.
- Classification performance measured on **LEDGAR** should not be interpreted as equivalent performance on these documents because the integrated documents are outside the original training distribution.
- Retrieval and generation errors remain possible.
- The system should **not be treated as a source of legal advice** or as a replacement for professional legal review.

## 12. Conclusion

Phase 8 successfully integrated the major components developed during Phases 1–7 into a single end-to-end pipeline.

### Final Run Summary

The final run processed:

- **2 documents**
- **17 clauses**
- **17 classified clauses**
- **6 flagged clauses**
- **13 clauses with extractions**
- **47 extracted items**
- **11 representative queries**
- **11 successful retrievals**
- **11 generated responses**
- **0 pipeline failures**

The complete run finished in **41.7 seconds**.

The integration demonstrates that document processing, classification, calibrated importance, attention flags, information extraction, semantic retrieval, RAG context construction, and grounded generation can operate as a **single traceable pipeline**.

More importantly, the evaluation exposes the distinction between **pipeline functionality and answer correctness**. Some queries produced useful grounded responses, while others demonstrated retrieval-ranking or generation-selection failures. This is consistent with the component-level limitations identified in earlier phases.

### Final Takeaway

> **Phase 8 demonstrates a functioning, traceable end-to-end NLP + Deep Learning pipeline with explicit failure handling and component-wise evaluation. It does not establish reliable legal correctness.**
